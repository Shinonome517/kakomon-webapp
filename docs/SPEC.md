# 一陸特 学習アプリ v0.1 — 製品・実装仕様書

版：1.0 / 作成日：2026-09-26 / 状態：実装開始可能

本書は機能と実装の正本です。特定の所有者・実環境の接続情報は含めません。初版の成功は「実問題をすべて収録すること」ではなく「問題を取り込めば、招待した利用者がスマホで学習できること」です。

## 2. 今回の設計基準と範囲

### 2.1 採用基準

フレームワークはユーザー未指定のため、実装を迷わせない基準として以下を採用します。

| 層 | 基準 |
|---|---|
| 言語・サーバー | Python 3.13、Django 5.2 LTSの保守中パッチ版、Gunicorn |
| 認証 | Django認証・DBセッション・CSRF。必要なログイン試行制限は保守中のライブラリを利用。 |
| DB | SQLiteをローカルSSD上に配置。単一アプリインスタンス。Django ORMとマイグレーション。 |
| UI | Djangoテンプレート＋小さなJavaScript。採点はfetchで更新、通常のPOSTも利用可能にする。 |
| 数式・静的資産 | KaTeXなどの保守中ライブラリをローカル配信。Node/npmは資産構築と必要な検証のみ。 |
| 実行 | アプリをDocker Composeで起動。ホストのNginxがIPv6 HTTPSを終端。 |
| バックアップ | SQLiteの整合性あるスナップショット＋画像・メタデータ。resticの暗号化SFTP保存。 |
| 開発 | Mac上でDockerなしに起動・テスト可能。uv、pytest、Ruff、Playwrightを基準とする。 |

Djangoの標準認証を利用して独自認証の実装量を減らします。SQLiteは小規模な単一サーバー向けの選択であり、無制限の同時書き込みを想定しません。対応バージョンとSQLiteの制約は公式資料[S01–S03]を参照してください。

依存は保守中の互換版を確認してlockファイルに固定します。Djangoを無断で別メジャーへ変更しません。Python依存は`uv.lock`、npm利用時は`package-lock.json`をコミットします。OS・ブラウザ・基盤の変更は作業端末で自動適用しません。

### 2.2 初版に含めないもの

模擬試験、タイマー試験、ランキング、他人の成績閲覧、公開サインアップ、メール、OAuth、決済、広告、オンラインAI解説生成、ネイティブアプリ、Service Workerによるオフライン回答、他資格の画面、問題のWeb編集は作りません。

実問題の収集、元PDFの自動ダウンロード、OCR、画像切り抜き、Astraによる本物の問題の解答作成は別の作業です。権利・正確性を確認した実データの投入も人間が後日行います。開発に使う合成問題には「動作確認用・試験対策用ではない」と表示します。

### 2.3 拡張のための境界

`accounts`、`questions`、`learning`、`operations`の責務を分離します。採点関数は画面に依存させず、問題リビジョンと選択肢IDから判定を返します。学習セッションには`mode='practice'`を持たせますが、他モードの画面や機能は未実装でよいものとします。汎用プラグイン機構は不要です。

## 3. アカウント・認証・権限

### 3.1 発行とパスワード

`AbstractUser`を継承するカスタムユーザーモデルを最初のマイグレーションから使います。メールは任意の空欄で、画面・CLIとも入力不要です。ユーザー名は小文字の英数字と`_ . -`、3～32文字に正規化し、一意にします。表示名は別の任意項目です。

管理用コマンドを用意します。

- `python manage.py create_learner --username <USERNAME>`：対話的・非表示入力でパスワードを設定。
- `python manage.py reset_learner_password --username <USERNAME>`：管理者による再設定。既存セッションを無効化。
- `python manage.py disable_learner --username <USERNAME>`：論理無効化。次のリクエストから利用不可。

パスワードをコマンド引数・ログ・固定seedに入れません。初回・管理者リセット後には本人のパスワード変更を必須とし、変更完了前は問題を閲覧できません。12文字以上、過度に短い／一般的なパスワードの拒否など、Djangoの検証を使います。独自ハッシュは不可です。Django標準の保守されているハッシャーを使います。[S01]

ユーザー向けにはログイン、POSTログアウト、本人のパスワード変更だけを用意します。初版でDjango adminを公開する必要はなく、`/admin/`はルート登録しません。OS上で管理コマンドを実行できる運用者と、アプリ利用者を区別します。

### 3.2 セッションと防御

DBセッション、`HttpOnly`、本番の`Secure`、`SameSite=Lax`、CSRF検証を使用します。セッションは原則14日で、有効期限の挙動をテストします。ログイン時のセッション更新、パスワード変更時の他端末無効化を標準機構で扱います。

ログイン失敗は「ユーザー名またはパスワードが違います」と統一し、存在するユーザー名を漏らしません。認証の再試行制限は、保守中の`django-axes`などを公式文書を確認して導入します。初期値は同一ユーザー名＋送信元の失敗5回／15分に加え、送信元単位の連続試行にも上限を設けます。永続ロックにせず、正常な他利用者への影響を確認します。

プロキシ越しの送信元を無条件に信じてはいけません。外側の接続元制限とNginxによるヘッダー上書きが成立する本番設定だけで、検証済みクライアントIPを試行制限に使います。開発ではソケットの接続元を使います。

### 3.3 閲覧権限

未ログインではログイン画面、最低限のヘルスチェック、公開してよいCSS／JSだけを返します。問題の本文、選択肢、説明、画像、出題数・成績APIは保護します。

履歴・ブックマーク・学習セッションはサーバーで認証中のユーザーに限定します。クライアントから渡された`user_id`は所有者決定に使用しません。存在を漏らしたくない他人のリソースは404とし、APIにHTMLログイン画面を200で返しません。

## 4. 画面と操作

### 4.1 画面

| 画面 | 主な内容 |
|---|---|
| ログイン | ユーザー名、パスワード、エラー表示 |
| 初回／通常パスワード変更 | 現在・新しいパスワードの適切な検証 |
| ホーム／出題設定 | 科目、年度・実施回、分野、対象条件、問題順／ランダム、件数 |
| 学習 | 問題情報、本文・図、選択肢、採点・解説、ブックマーク、次へ |
| 成績 | 最新回答正答率、正解数／回答済み問題数、学習済み／対象総数、科目・分野別 |
| 復習 | 最終不正解、未回答、ブックマークの条件から開始 |

本書の「年度」は西暦の実施年とします。元の和暦表記は表示名に保持できます。科目別に実施回や問題数が異なる可能性に対応し、開催月を固定しません。

### 4.2 出題の条件

科目は無線工学・法規・両方。実施回と分野は複数選択可。初期値は全て、元の問題順です。順序は実施日相当のソートキー、科目、問題番号を使い、表示ラベルの文字列順だけに依存しません。

復習条件は「すべて」「最終不正解」「未回答」「ブックマーク」の一つを選び、科目・実施回・分野条件とはANDで結合します。ブックマークは正解・不正解から独立します。

件数は10・20・50・すべてから選べ、初期値10、母集団が少なければ全件とします。これは未指定部分の設計既定値です。0件なら空状態を表示し、開始ボタンを無効にします。ランダムは抽出後のキューをサーバー側で保存し、同一セッション内で重複させません。

### 4.3 即時採点と通信失敗

画面状態は`未回答 → 送信中 → 採点済み`です。選択肢全体を44px以上のタップ領域にし、押した時点で送信します。別の「回答する」ボタンは置きません。キーボードでの選択肢ボタン操作も同じ挙動にします。

送信開始後は全選択肢を無効化します。サーバー保存が成功するまで正誤は確定表示しません。成功時は選んだ回答、正誤、正解、解説を表示し、**自動で次の問題へ移動しません**。利用者が「次の問題」を押します。

タイムアウト時は「保存状況を確認できません。同じ回答を再送します」と表示し、同じ学習項目IDで再試行します。失敗したPOSTの代わりに新しい回答IDを作りません。回答内容をlocalStorageへ恒久保存せず、ページ再取得で保存済み結果を回復できるようにします。サーバーの再読み込みで未保存と分かった場合に限り再選択を可能にします。

同じ問題を解き直す場合は、明示的に新しい学習項目を作ります。戻る・更新・再送だけでは新しい回答を記録しません。

### 4.4 スマホ・見た目

360px幅から利用でき、本文16px以上、行間1.6以上、操作領域44px以上を基準にします。画面全体の横スクロールを避け、大きな図と長い数式だけ局所的に拡大／スクロールできるようにします。

過去問道場系の落ち着いた緑・白・薄い黄／橙を連想する独自パレットを用います。既存サイトの色を測定した値ではなく、今回のデザイン指定です。

| トークン | 色 | 用途 |
|---|---|---|
| primary | `#276749` | 見出し、主ボタン、選択状態 |
| background | `#F7F9F5` | ページ背景 |
| surface | `#FFFFFF` | 問題カード |
| soft | `#EDF5E8` | 補助領域 |
| accent | `#FFF4D6` | 解説の背景 |
| text | `#1F2937` | 本文 |
| error | `#B42318` | 不正解・エラー |

ロゴ、名称、マスコット、HTML、CSS、画像、説明文は既存サイトからコピーしません。「公式」「公認」と誤認する表示をしません。色だけで正誤を伝えず、「正解」「不正解」と記号を併記します。コントラスト、フォーカス、スクリーンリーダー向け結果通知、画像モーダルのフォーカス復帰をテストします。

外部フォント・広告・解析SDKは使わず、日本語のシステムフォントを基本にします。ダークモードは初版の必須条件ではありません。

## 5. 問題・解説・画像

### 5.1 内容モデル

初版の出題形式は単一選択だけです。選択肢は2～10個を許容し、4択に固定しません。将来の複数選択は`question_type`追加で拡張可能にしますが、未対応形式の取り込みはエラーにします。

本文・解説は、Markdownブロックと画像ブロックの順序付き配列で表現します。各選択肢も同じブロック列を持てます。

```json
[
  {"type":"markdown","text":"次の図について答えてください。"},
  {"type":"image","asset_id":"figure-1","alt":"問題で参照する接続図"},
  {"type":"markdown","text":"条件は $R = 10\\,\\Omega$ とします。"}
]
```

Markdownの生HTML・外部画像・iframe・scriptは許可しません。許可する要素を限定してサニタイズします。数式はインライン`$...$`と独立`$$...$$`を扱い、レンダラーで任意HTMLや外部アクセスを有効にしません。

選択肢は表示位置とは別の安定した`choice_id`を持ちます。初版では選択肢を並べ替えません。正解はサーバー側にのみ置き、未回答のHTML、JSON、data属性、JSバンドル、プリロードに含めません。解説と解説だけに属する画像も回答前には配信しません。

### 5.2 画像の保存と配信

画像ファイル自体はDBにBLOB保存せず、永続ボリュームの`media/`に保存します。DBには保存キー、SHA-256、形式、寸法、表示順、代替テキスト、問題リビジョンとの対応を格納します。1つの論理DBでユーザー・問題・履歴テーブルを分けます。

取り込みで認める形式はPNG、JPEG、WebPです。SVG、HTML、GIF等は初版では拒否します。拡張子だけでなくデコード結果も確認し、サイズ・総ピクセル数の上限を設けます。初期上限は1画像20MiB・30メガピクセルです。EXIF等の不要なメタデータを除去した保存画像のハッシュを取ります。

保存先は内容ハッシュによる不変キーとし、同名上書きを避けます。画像の自動削除・GCは初版では行いません。別ユーザーや旧リビジョンへの意図しない漏洩を避けるため、ファイルパスを直接URLにしません。

画像は認証済みビュー経由で配信し、その画像への参照元問題が公開中か、利用者が当該リビジョンの解説を閲覧できるかを確認します。推測しにくいURLだけを認証の代わりにしません。`public/`や無認証のNginx `/media/` aliasは不可です。

ブラウザへは`Cache-Control: private, no-store`を付けます。学習データを含むHTML/API/画像をCloudflareで共有キャッシュしません。ローカルキャッシュ制約よりも私的データの分離を優先します。一般のCSS/JSのみハッシュ付き長期キャッシュを許可します。

## 6. DBと最新回答の定義

### 6.1 論理テーブル

名称の細部は変更できますが、責務と制約は維持します。

| エンティティ | 主なフィールド／制約 |
|---|---|
| User | UUID等のID、正規化username UNIQUE、password hash、display_name、is_active、must_change_password |
| ExamPaper | qualification_code、exam_year、session_code、session_label、subject、sort_key。科目別試験を一意化。 |
| Topic | subject、code、label、sort_order。初版は問題ごとに主分野1つ。 |
| Question | stable_id UNIQUE、exam_paper、question_number、topic、status、current_revision、grading_version |
| QuestionRevision | question、revision_number UNIQUE組、grading_version、type、stem_blocks、choices、correct_choice_id、explanation_blocks、source/review metadata |
| Asset | hash UNIQUE、storage_key、MIME、width、height、byte_size。不変ファイル。 |
| RevisionAsset | revision、asset、local_asset_id、用途／参照ブロック。 |
| StudySession | user、mode=practice、条件スナップショット、順序、作成日時、終了日時 |
| StudyItem | session、position UNIQUE組、question_revision、opaque token／ID、状態 |
| AnswerAttempt | 増加する整数ID、user、study_item UNIQUE、question、revision、grading_version、selected_choice_id、is_correct、answered_at |
| Bookmark | user＋question UNIQUE、created_at |
| ImportBatch | bundle_id、checksum、実行日時、結果、件数。秘密値を含まない。 |

DjangoのDBセッションとログイン制限用テーブルも同じDB内に置きます。生パスワードを保持する別テーブルは作りません。

### 6.2 集計

ユーザーと論理問題ごとに、現行`grading_version`に対応する有効な回答のうち、サーバーで確定した`AnswerAttempt.id`が最大のものだけを使います。クライアント時刻は使いません。IDはトランザクション内で採番し、更新・再利用しません。

```text
最新回答正答率 = 最新の有効回答が正解の問題数 / 有効回答済みの問題数 × 100
学習進捗 = 有効回答済みの問題数 / 公開中の対象問題数
```

未回答は正答率の分母に入れません。0件なら正答率は「—（未回答）」です。百分率は小数1桁とし、同時に整数の分子／分母を表示します。

例：Aを不正解→正解、Bを不正解と回答すると、AとBの最新2問で1/2＝50.0%です。全3回答の1/3ではありません。Bを正解にすると2/2＝100.0%です。未回答Cを追加しても正答率は100.0%のままで、進捗は2/3になります。

全体・科目・分野・出題条件別で同じ定義を使います。非公開・取り下げ問題は現在の集計から除外しますが、過去の履歴そのものは削除しません。ブックマークしても正答率は変わりません。

### 6.3 問題改訂

安定IDを維持したまま、新リビジョンを追加します。解説のみの修正では`grading_version`を変えず、過去の採点を維持します。

問題本文、選択肢、正解、採点に影響する図の変更は原則`grading_version`を増やします。古い履歴は当時の問題と判定のまま保存し、新版の現在集計では未回答として扱います。「改訂のため再学習」と表示します。古い正誤を黙って書き換えません。

既存の学習項目と現行採点版が食い違った状態で送信された場合は、採点せず409相当で最新版の再表示を促します。リビジョン変更によってブックマークの論理問題への対応を失わないようにします。

### 6.4 二重送信と並行処理

サーバーが発行したStudyItemを1回の回答権として使います。回答POSTにユーザー所有、問題リビジョン、選択肢の所属を検証し、`study_item`のUNIQUE制約で二重保存を防ぎます。

同じStudyItem・同じ選択肢の再送には、元の結果を返します。別の選択肢での再送は既存結果付きの409とし、書き換えません。別タブ・二重クリック・成功後の通信切断も同じ制約で処理します。

SQLiteでは`select_for_update()`を排他の根拠にしません。短い`transaction.atomic()`、DBの一意制約、適切な`IMMEDIATE`モードとbusy timeoutを使用します。画像デコード、HTTP通信、テンプレート描画をDBの書き込みトランザクション内に置きません。`ATOMIC_REQUESTS`による全リクエスト長時間ロックを避けます。[S03]

複数接続による競合を実ファイルDBでテストし、メモリDBの単一接続だけで確認を済ませません。性能不足が測定された場合はPostgreSQL移行を別タスクとして報告し、夜間に構成を無断で大きく変更しません。

## 7. 問題データの取り込み契約

### 7.1 バンドル

初版は展開済みディレクトリを入力とします。ZIP自動展開やブラウザアップロードは不要です。

```text
<bundle>/
  manifest.json
  assets/
    figure-1.png
    figure-2.webp
```

`manifest.json`は`schema_version: 1`、`bundle_id`、試験・分野定義、問題配列を持ちます。各問題には`stable_id`、試験ID、番号、分野、出題形式、本文ブロック、選択肢配列、正解ID、解説ブロック、画像一覧、確認状態、出典メタデータを持たせます。

正式なJSON Schemaと合成サンプルを実装時に`schemas/`と`tests/fixtures/`へ追加してください。実PDFの位置や切り抜き操作をChatGPTへ指示する文書は今回作りません。

### 7.2 コマンド仕様

```sh
python manage.py import_questions <BUNDLE_DIR> --dry-run
python manage.py import_questions <BUNDLE_DIR>
```

dry-runは本番DB・mediaを変更せず、追加／変更／変更なし／非公開／エラー件数を表示します。同じバンドルの再取り込みは無変更とし、問題・画像・回答履歴を二重作成しません。異なる内容で同じIDが来た場合は改訂規則に従います。

JSON Schemaに加えて、重複ID、選択肢数、唯一の正解、参照整合性、画像の存在・形式・容量、パストラバーサル、絶対パス、シンボリックリンク、バンドル外への参照、未知の出題形式を検証します。URLから任意ファイルを自動ダウンロードしません。

画像を安全な一時領域で検証し、不変キーでmediaに配置してからDBを一括更新します。バンドルの一部だけを公開する状態を作りません。DB更新失敗時の未参照画像は許容しますが、参照先の存在しない公開問題を作ってはいけません。

### 7.3 確認フロー

`draft`／`verified`／`withdrawn`を区別します。公式解答との照合と解説の確認が済んだもののみ`verified`として公開します。AI生成の解説であること、確認状況、取得元・問題番号・ページなどの来歴を保持します。元PDFはWeb配信・Git同梱しません。

解答不一致・複数正解疑い・図の欠落・不正な数式は勝手に補完して公開せず、draftとして取り込みレポートへ出します。アプリはAstraへ問い合わせる機能を持ちません。

## 8. 外部公開と永続化

### 8.1 目標構成

```text
利用者（IPv4 / IPv6）
  → Cloudflare（HTTPS、プロキシ付きAAAA）
  → N100のグローバルIPv6:443（Cloudflare送信元だけ許可）
  → ホストNginx（TLS終端）
  → 127.0.0.1:18080
  → Docker内のGunicorn / Django
  → ローカルSSDのSQLite・media
```

CloudflareのAAAAプロキシ・IPv6対応・Origin CAは無料プランを前提に利用可能です。ただし設定やサービスの提供条件は適用時に公式資料を確認します。[S04–S07]

### 8.2 DNSとTLS

Webホスト名のAAAAをDDNS対象とし、`proxied=true`を維持します。公開用IPv4のAレコードは必須にしません。Cloudflareの利用者側をIPv6限定にするレコード設定は有効化せず、通常のIPv4／IPv6両対応を保ちます。利用者側のアドレス種別とオリジン側のアドレス種別は別です。[S12] HTTP以外のSSHやVPN用レコードを、このWebプロキシと混同しません。

TLSモードは**Full (strict)**。Nginxに対象ホスト名のCloudflare Origin CA証明書または適切な公開CA証明書を設定します。Flexibleは不可です。Origin CA利用時にプロキシをOFFにすると、通常のブラウザから直接は証明書を信頼できない点を運用文書へ記載します。[S06–S07]

NginxはIPv6の443で待ち受け、プレフィックス変更のたびに固定アドレスへ再bindする構成にしません。自宅ルーターとホストの両方に着信許可が必要です。IPv6でNAPTのポート転送が不要でもFW許可は必要です。CFの現行IPv6送信元レンジのみを許可し、一覧更新の失敗で全許可にしません。

本番DNS名は環境変数で渡します。ドメイン、API token、zone/record ID、Origin証明書・秘密鍵、DDNSのNIC・アドレス選択条件はGitに含めません。

### 8.3 DDNSテンプレート

systemd timerと更新スクリプトのテンプレートを作ります。初期周期は5分。Linuxのインターフェースから有効な安定GUAを選び、temporary、deprecated、tentative、dadfailed、ULA、リンクローカルを除外します。複数候補を一意に決められない場合は更新を見送り、設定を求めるエラーを出します。

公開DNSをdigしてもCloudflare側のIPが返るため、それをオリジンの現在値比較に使いません。DNS APIで対象レコードを読み、差がある場合だけPATCHします。record IDを固定し、別のレコードを作成・削除しません。更新後も`proxied=true`とAuto TTLを維持します。[S04, S08]

トークンは対象ゾーンのDNS編集に限定します。最小権限がレコード単位であるとは決めつけません。secretファイルで受け取り、引数・ログに出さず、ネットワーク失敗を有限回の再試行と非ゼロ終了で扱います。実API呼び出しは人間だけが行います。

### 8.4 ホスト・コンテナ

Composeはアプリのポートを`127.0.0.1:18080:8000`にのみ公開します。`0.0.0.0:8000`や全インターフェースのDB公開は不可です。Nginxはホストサービスとし、Dockerのポート公開がUFWを迂回する問題を減らします。Dockerのネットワーク挙動については適用時にも確認します。[S09]

アプリは非root、専用の永続ボリューム／ディレクトリ、ヘルスチェック、ログローテーションを使用します。Dockerソケットはマウントしません。DBとmediaはイメージに含めず、再作成後も残します。SQLiteはNFS／SMB／同期フォルダーに置きません。

Nginxは許可したHost以外を拒否し、アプリへ送るHost・転送プロトコル・クライアントIPを固定方針で上書きします。`X-Forwarded-For`を利用者入力のまま継承しません。実IP書き換えとCloudflare送信元ACLの順序が衝突しない構成を作り、元の接続元に基づく制御を検証してください。

本番ではDEBUG=False、正確なALLOWED_HOSTS／CSRF_TRUSTED_ORIGINS、HTTPS強制、安全なcookieを必須にします。開発用の弱い設定への自動フォールバックはしません。秘密値が不足した本番起動は失敗させます。

動的ページと認証画像はCloudflareでキャッシュをバイパスし、Cache Everythingを適用しません。未ログイン状態と異なる二つのアカウントで、別セッションのデータが再利用されないことを公開前に確認します。

## 9. バックアップ・復元

### 9.1 方針

日次、初期時刻は日本時間03:30、RPOの目標は24時間です。停止や回線断でこれを超える可能性を明記し、最終成功時刻を確認できるようにします。別拠点へ到達できなければ成功扱いにしません。復旧は手動、RTOは初版では保証しません。

送信元ホストからTailscale経由のSSH/SFTPで別拠点へ接続し、resticの暗号化リポジトリへ保存します。SSHのホスト鍵を検証し、StrictHostKeyCheckingを無効にしません。SSH設定済みという前提でも、**バックアップ実行ユーザー・送信元ホストから**無人接続できるかは別途確認します。[S10]

### 9.2 内容と整合性

対象はSQLiteの全テーブル、画像、取り込み来歴、バージョン情報、復元に必要な設定・秘密情報です。秘密情報は暗号化バックアップ内または別の安全な保管場所に置き、Gitには置きません。resticの復号パスワードはバックアップ元だけに保存せず、別の安全な場所にも保管します。

稼働中のSQLiteファイルを単純なcp/rsyncでコピーしません。SQLiteのオンラインバックアップAPI等でスナップショットを作り、integrity_checkを実行します。DBのスナップショット取得後に参照先の不変画像を収集し、存在・ハッシュを確認します。画像GCは初版で禁止し、DBと画像の時点差による参照切れを防ぎます。

エクスポートは一時ディレクトリにDB・参照画像・manifestをそろえてから完了扱いとし、resticに渡します。タイマーの重複実行を排他し、途中失敗は非ゼロ終了、最後に成功したバックアップを残します。転送先を`--delete`でミラーリングしません。

初期保持案は日次14・週次8・月次3。保持とpruneは初期化・接続検証後に人間が有効化します。保存先の容量・ストレージ耐久性は適用時に確認します。テストでは本物の遠隔ホストへ接続しません。

### 9.3 復元テスト

まず隔離したローカル一時ディレクトリへ復元し、DB integrity、ユーザー件数、問題件数、最新回答の集計、画像のハッシュ・表示を確認します。復元DBの既存セッションは無効化する手順を記載します。本番データへ自動上書きしません。

ローカルエクスポート／復元は自動テスト必須です。実際の遠隔SFTP・日次実行・復号鍵保管の検証は人間のデプロイチェックとして区別します。

## 10. 品質・完了

自動テストは `docs/ACCEPTANCE.md` に従います。開発用SQLiteを使うだけでなく、競合に関わるケースは実ファイルDBと複数接続で検証します。E2Eは合成問題・架空ユーザーだけで動かします。

非本番の測定条件を明記し、モバイル幅360／390／768pxとPC幅で確認します。目標は小規模利用者が待たずに一問ずつ学べることです。N100実機を測っていない性能値を保証として記載しません。バックグラウンドの無限ジョブや常時AI呼び出しを追加しません。

実装後、READMEに実際に成功したコマンド、必要な環境変数名、アカウント発行、import、export/restore、開発起動手順を追記します。デプロイと秘密値の準備は人間が行うため、本番未接続でも開発実装を完了とできます。ただし未検証事項を明示します。
